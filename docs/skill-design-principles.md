# Skill 设计原则

> Skill 是教科书,不是菜谱。读完之后,使用者面对从未见过的场景也能自己判断该怎么办。

---

## 一、核心理念:教方法论,不教步骤

一个好的 skill 传递的是**专家的思维方式**,而不是专家的操作记录。

区分标准很简单:如果使用者遇到一个 skill 中没有列举过的场景,他能不能根据 skill 教的东西自己做出正确判断?能,就是好 skill;不能,就只是一份代码片段合集。

具体来说:

- **教"为什么"**,而不只是"怎么做"。规则背后的原理比规则本身更重要--理解了原理,使用者能在新场景中自己推导出正确做法。
- **教"怎么判断"**,而不只是"做什么"。给出决策框架和诊断方法,让使用者能分析当前情况属于哪类,而不是穷举所有情况。
- **教"什么时候不该做"**,而不只是"该做什么"。专家知识的很大一部分是知道边界在哪--什么情况下常规方法会失效,什么时候需要换一种思路。

反面案例:一个 PDF 处理 skill 罗列了"合并用这段代码、拆分用那段代码、加水印用这段代码"--这只是 API 文档的搬运。
正面案例:一个 PDF 阅读 skill 教你"拿到一个 PDF,先做内容诊断(pdfinfo + 采样文本 + 检查嵌入图像),根据诊断结果选择阅读策略--文本密集型走文本提取、扫描件走光栅化+OCR、数据密集型先试表格提取再看图"--这是方法论。

## 二、原子性原则：skill 是独立专业知识，不是流水线节点

> **与引擎的分层**：在 YoungFlow 架构中，skill 是 flow 资产包的一部分，但它不应该知道自己“在哪条流水线中”。输出路径、上游产物位置、schema 文件路径等运行时信息由工作上下文（Flow Prompt）提供，skill 中用“工作上下文中指定的 XX”来引用，不硬编码具体路径。

一个 skill 应该在任何执行上下文中都能让使用者把任务做好--无论它被单独使用、被嵌入某条流水线、还是被放进一个与设计时完全不同的系统中。

### 1. 不假设调用方

skill 中不应出现:
- 特定流程的阶段编号或节点名称("Phase 10"、"feature_aggregator_20")
- 对特定上下游的引用("下游枚举器"、"供 Phase 12 使用")
- 假设存在特定消费者("下游消费者依赖此字段来决定...")

**检验方法**:把 skill 从当前流程中拔出来,放到一个完全不同的场景下使用。skill 中的每一句话是否仍然成立?如果某句话只在特定流水线中才有意义,它就不该在 skill 里。

### 2. 价值标准自足

skill 的质量标准必须用任务本身的准确性来定义,不能用外部影响来论证。

- ✗ "分类错误会导致下游漏检" → 用外部后果论证,换个下游就不成立
- ✓ "分类错误意味着画像不准确--类型漏标就是丢失信息" → 任务本身的准确性

**原理**:如果一个 skill 需要靠"下游会怎样"来解释自己为什么重要,说明它没有想清楚自己的任务本身为什么需要做好。专家做画像做得准,不是因为"后面有人要用",而是因为准确本身就是画像的专业标准。

### 3. 方法论与输出格式分离

skill 教的是**搞清楚什么**和**怎么搞清楚**，不规定**输出成什么结构**。

- ✗ “在 `dynamic_dispatch` 数组中记录每个分发点” → 规定了字段名和数据结构
- ✓ “画像中应记录每个分发点的入口位置、分发机制、实现代码所在目录” → 说清楚要记录什么信息

**原理**：输出格式是调用方的契约（由 schema、orchestrator 或使用者自己决定），不是专业方法论的一部分。一个安全专家知道“要搞清楚项目有没有动态分发”，但“这个信息放在 YAML 的哪个字段里”不是专业知识，是工程约定。

**实践补充**：schema 文件应统一存放在 flow 资产包的 `schemas/` 目录下，不应放在单个 skill 目录内。工作上下文通过 `${schemas}/xxx.schema.yaml` 变量提供路径，skill 中只需写“工作上下文中指定的 schema 文件”。

### 4. Frontmatter 简洁

SKILL.md 的 YAML frontmatter 只保留两个字段：

```yaml
---
name: Project Profiler
description: 项目画像技能 - ...
---
```

## 三、结构原则

### 1. 先建立心智模型,再给操作指引

Skill 的结构应该遵循认知顺序:

```
为什么需要这个 skill(这类问题的本质困难是什么)
    → 核心概念和分类框架(这个领域的问题可以分成哪几类)
        → 诊断方法(面对一个具体问题,怎么判断它属于哪类)
            → 每类问题的处理策略(原理 + 关键步骤)
                → 陷阱和边界条件(专家踩过的坑)
```

不要上来就给操作步骤。使用者需要先理解"我在解决什么性质的问题",才能正确运用后面的工具和方法。

### 2. 渐进式信息披露

不是所有信息都需要一次性呈现。按需加载:

- **触发层**(description,~100词):什么时候该用这个 skill。永远在上下文中。
- **决策层**(SKILL.md 主体,<500行):诊断框架和核心策略。触发后加载。
- **执行层**(refs/ 目录下的参考文件):具体实现细节、代码示例、框架特定指南。在决策层中用明确指引告诉使用者"如果你需要 X,去读 refs/X.md"。

原则是:SKILL.md 教你做什么决策,refs/ 教你怎么执行决策。

### 3. 边界定义要像合同条款一样精确

一个 skill 的"不做什么"和"做什么"同等重要:

- 在 description 中明确写出 `Do NOT use this skill for...`
- 当存在容易混淆的相关 skill 时,说明两者的分界线
- 当 skill 的能力到达边界时,明确指向"接下来该去哪"

这不是防御性写作,而是帮助使用者快速判断"我是不是来对了地方"。

## 四、内容原则

### 1. 诊断先于行动

每个 skill 都应该有一个"诊断阶段"--在动手之前,先搞清楚当前面对的是什么情况。

好的诊断框架包含:
- **检查什么**:需要收集哪些信息来判断情况
- **怎么分类**:收集到的信息对应哪种类型的问题
- **各类型的特征**:每种类型的典型信号是什么

诊断的目的是让使用者在采取行动之前就知道自己面对的是哪类情况,避免用错误的方法处理问题。

### 2. 用原理解释规则

每条重要规则都应该附带它存在的原因。不是"你必须这样做",而是"因为 X 原理,所以这样做才能避免 Y 问题"。

这么做的理由:
- 理解原理的使用者能在规则未覆盖的场景中正确推理
- 原理比规则更容易记住
- 当两条规则冲突时,理解原理才能做出正确取舍

**注意:原理应来自任务本身,而非来自外部系统的反应。** "C/C++ 优先于 cli-sdk,因为两者描述的特征维度不同"是好的原理;"C/C++ 优先于 cli-sdk,因为下游会触发不同的分析策略"是把原理外包给了调用方--换一个调用方,这个"原理"就失效了。

### 3. 陷阱和边界条件是最高价值的内容

专家和新手的核心差距不在于"知道怎么做",而在于"知道什么时候常规做法会出问题"。

好的 skill 会主动标注:
- **常见误区**:看起来正确但实际上会出问题的做法,以及为什么会出问题
- **边界条件**:方法论在什么条件下失效
- **代价和取舍**:不同策略各自牺牲了什么,什么情况下应该选择哪种取舍

这些内容来自实践经验的积累,是 skill 中最难被替代的部分。

### 4. 示例服务于理解,而非替代思考

示例的作用是帮助使用者理解抽象概念,而不是给他们复制粘贴的模板。

好的示例:
- 展示一个原则在具体场景中如何被应用
- 包含关键的判断过程("这里之所以选 A 而不是 B,是因为...")
- 选择有代表性的场景,而非简单场景

差的示例:
- 只展示最终结果,不展示推理过程
- 过于简单,无法帮助理解真实场景中的复杂性
- 过多的示例变成了穷举,暗示"照抄就好"

## 五、触发设计原则

Description 是 skill 的入口。它决定了 skill 在什么时候被激活。

### 1. 覆盖用户表述的自然变体

用户不会用 skill 的术语来描述问题。description 要用用户的语言写,覆盖他们可能使用的各种说法。

### 2. 适度"推"一些

使用者(如 LLM)倾向于不触发 skill,所以 description 可以写得积极主动一些,主动列举应该触发的场景--包括那些不那么显而易见的场景。

### 3. 互斥要显式声明

当多个 skill 的领域相邻时,在 description 中明确写"Do NOT use for X, use Y skill instead",避免歧义。

## 六、质量检验标准

写完一个 skill 后,用这几个问题检验:

1. **举一反三测试**:拿出一个 skill 中没有直接覆盖的场景,使用者能否根据 skill 教的方法论推导出正确做法?
2. **删除测试**:如果删掉所有代码示例,skill 是否仍然传递了最核心的价值?如果是,说明方法论部分写得好;如果不是,说明过度依赖示例。
3. **新手测试**:一个对该领域不熟悉的使用者,读完 skill 后能否理解"为什么要这样做"?还是只知道"要这样做"?
4. **专家测试**:一个该领域的专家读完后,是否会说"是的,这就是我做判断的方式"?还是会说"这只是表面操作流程"?
5. **拔插测试**:把 skill 从当前使用场景中拔出来,放到一个完全不同的系统中。skill 的每一句话是否仍然成立?如果有句子只在特定流水线中有意义,那就是耦合。
6. **动机测试**:检查 skill 中每个"为什么重要"的论述。它的理由是来自任务本身("画像准确才完整"),还是来自外部系统("下游会漏检")?后者意味着 skill 没有立住自己的价值。
