# 数据格式扫描方法论

## 任务目标

在指定范围内发现所有数据格式的解析与转换代码，输出完整的格式清单。完整性是第一优先级——宁可多报，不可漏报。

## 方法论

### 搜索完整性

- **多角度交叉验证**：对同一类格式，用至少 3 种不同的搜索模式验证（库名、函数名、配置项）
- **不截断搜索结果**：禁止对搜索结果做 head/tail 截断。如果结果过多，按子目录分批搜索缩小范围
- **目录广度覆盖**：扫描所有源码目录。monorepo 中每个包都要检查
- **动态分发目录**：如果 profiler 标记了 `dynamic_dispatch`，`implementation_dirs` 下的模块可能包含独立的数据处理逻辑，不要跳过

### 扫描维度

根据项目实际使用的语言和框架，覆盖以下维度（自行确定搜索关键词）：

- 结构化数据解析（XML、JSON、YAML、CSV、INI 等）
- 序列化/反序列化（显式函数调用 + 框架隐式配置）
- 模板引擎渲染
- 表达式/查询引擎（表达式求值器、SQL 构建器等）
- 嵌入式脚本引擎（Lua/V8/Wasm 等）
- HTML/DOM 操作（XSS sink）
- 编码转换与数据结构变换
- 自定义紧凑编码/内部序列化格式
- 持久化存储路径构造
- C/C++ 项目：系统性扫描公开头文件的数据变换 API

### 模板引擎渲染扫描（强制要求）

对于使用模板引擎（如 Blade、Twig、Smarty、Jinja2 等）的项目，**必须系统性扫描所有视图/模板文件**，不能仅依赖关键词匹配。具体要求：

1. **枚举所有模板文件**：先枚举 `views/` 目录（或对应框架的模板目录）下的所有模板文件，确保每张视图都被扫描
2. **关联路由与视图**：追踪每个 HTTP 路由对应的渲染函数（如 `$this->renderPage($response, 'viewname')`），确认对应的视图文件已被扫描
3. **扫描所有潜在 XSS sink**：对每张视图文件检查以下危险模式：
   - `{!! !!}` / `{{{ }}}` 等原始输出语法（模板引擎默认转义语法之外）
   - `{{ variable }}` 输出到 data-* HTML 属性，且该属性值被同一页面的 JavaScript 读取（如 `element.dataset.attr` 后直接拼接进 DOM 或 alert）
   - `json_encode()` / `@json` / `@entangle` 等将数据传入 `<script>` 块或 JavaScript 上下文
   - 动态拼接 HTML 字符串（如字符串模板、字符串拼接形式的 `$html .= ...`）
   - 服务器端模板中的 JavaScript 事件处理器绑定（如 `onclick="{{ $var }}"`)
4. **跨文件追踪**：模板中的数据通常来自控制器。追踪 controller → view 的数据传递，确认数据来源（数据库、用户输入等）

**常见遗漏场景**：视图文件使用 `{{ $var }}`（看似安全）输出到 `data-*` 属性，但页面的 JS 用 `dataset` API 读取后直接拼接进 DOM（如 `bootbox.alert`、`innerHTML` 赋值）。这种上下文转移使得看似转义过的输出仍然危险。必须覆盖所有 data 属性读取路径。

### 验证要求

- 搜索命中必须验证：确认是实际的解析/转换调用，不是注释、测试或类型声明
- 对大文件或搜索结果密集的文件，Read 确认上下文

## 输出格式

每种格式一条记录：

```
格式名称 | 风险等级(safe/low/medium/high) | 发现位置(file:line) | 使用场景 | 安全备注
```
