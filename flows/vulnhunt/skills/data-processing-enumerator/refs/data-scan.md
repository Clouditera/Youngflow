# 数据格式扫描方法论

## 任务目标

在指定范围内发现所有数据格式的解析与转换代码，输出完整的格式清单。完整性是第一优先级——宁可多报，不可漏报。

## 方法论

### 搜索完整性

- **多角度交叉验证**：对同一类格式，用至少 3 种不同的搜索模式验证（库名、函数名、配置项）
- **不截断搜索结果**：禁止对搜索结果做 head/tail 截断。如果结果过多，按子目录分批搜索缩小范围
- **目录广度覆盖**：扫描所有源码目录。monorepo 中每个包都要检查
- **动态分发目录**：如果 profiler 标记了 `dynamic_dispatch`，`implementation_dirs` 下的模块可能包含独立的数据处理逻辑，不要跳过

### 扫描维度

根据项目实际使用的语言和框架，覆盖以下维度（自行确定搜索关键词）：

- 结构化数据解析（XML、JSON、YAML、CSV、INI 等）
- 序列化/反序列化（显式函数调用 + 框架隐式配置）
- 模板引擎渲染
- 表达式/查询引擎（表达式求值器、SQL 构建器等）
- 嵌入式脚本引擎（Lua/V8/Wasm 等）
- HTML/DOM 操作（XSS sink）
  - **特别注意**：用户提交内容（description、bio、readme 等）经 Markdown 渲染后在 profile 页面输出，是 Stored XSS 的经典攻击面。必须搜索以下组合：
    - `markdown.RenderString` + 用户模型字段（如 `User.Description`）+ `ctx.Data["RenderedXxx"]`
    - `template.HTML` 返回模式（`return template.HTML(...)`）作为高风险 XSS sink 指标
    - HTML sanitizer 配置中允许的危险元素（如 SVG、on* 事件属性）
- 编码转换与数据结构变换
- 自定义紧凑编码/内部序列化格式
- 持久化存储路径构造
- C/C++ 项目：系统性扫描公开头文件的数据变换 API

### 验证要求

- 搜索命中必须验证：确认是实际的解析/转换调用，不是注释、测试或类型声明
- 对大文件或搜索结果密集的文件，Read 确认上下文

## 输出格式

每种格式一条记录：

```
格式名称 | 风险等级(safe/low/medium/high) | 发现位置(file:line) | 使用场景 | 安全备注
```
