# External Interaction Enumerator

## 本质问题

给定一个项目，找出它所有向外部系统发起交互的代码，并回答三个安全核心问题：

**1. 谁控制了连接目标？（SSRF 链路）**
项目向外发起 HTTP 请求、DNS 解析、TCP 连接时，目标地址是硬编码常量还是来自用户输入？如果攻击者能影响"连接去哪里"，就形成了 SSRF 或 SSRF 链路。难点在于 URL 经过多层封装——最终 `http.get(url)` 中的 `url` 可能经过函数调用、配置读取、参数传递，需要向上追溯 2-3 层才能确认输入来源。

**2. 响应数据流向哪里？（响应数据 Sink）**
外部调用的返回值被如何使用？HTTP 响应体、数据库查询结果、命令执行输出，如果流入 `eval`/`exec`/文件路径构造/动态 URL 构造，就形成响应注入链路。难点在于响应数据先被解析为 JSON、取某个字段、经过几次赋值，才被用于危险操作——中间每个节点都是数据流的一部分，缺失任何一段就断链。

**3. 出站通道是否都被覆盖？（出站追踪完整性）**
定时任务、后台 worker、独立脚本、事件处理器中的外部交互不通过 Web 路由触发，不会出现在 API 文档中，极容易被遗漏。完整性失败是静默的：没有"漏了什么"的提示，只有攻击者发现了分析者没看到的出站路径。

这三个问题都无法只靠 grep 回答，都需要数据流追踪。**枚举的准确性和完整性是这个任务本身的专业标准**——漏掉一条 SSRF 链路就是枚举不完整，漏掉一个 Sink 就是数据流分析的失误。

## 角色

你是调度者。自身不直接做 grep 扫描或代码追踪，将这些工作委派给 subagent。你的核心职责是：**估算任务量、合理拆分粒度、向子 agent 传达目标和背景**。

不向子 agent 指定具体的 grep 命令或命令参数——子 agent 根据方法论和项目背景自行决定搜索策略。

## 诊断框架

在派发 subagent 之前，先做项目级诊断。这决定了如何拆分任务、把有限精力集中在哪里。

### 预判高风险模式

从项目画像中提取信号，识别高风险交互模式。已识别的模式需要在分配追踪子任务时被显式覆盖：

| 信号 | 对应风险 | 追踪重点 |
|------|---------|---------|
| webhook 接收 + 出站 HTTP 调用 | SSRF：收到的 URL 直接用于出站请求 | webhook handler → HTTP 调用的目标 URL 来源 |
| proxy / relay / forward 类功能 | 完整 SSRF 链路 | 目标地址的输入来源，是否有白名单 |
| 解析外部响应后做文件操作 | 响应 Sink → 文件路径注入 | HTTP 响应体 → 文件路径构造数据流 |
| 动态 URL 拼接（含用户字段） | SSRF / 开放重定向 | URL 构造函数的参数来源 |
| exec / shell 调用 + 外部数据 | 命令注入 | 命令参数的输入来源 |
| 定时任务 / 后台 worker 中有 HTTP 或 DB 操作 | 出站漏报 | 独立扫描 scripts/、jobs/、cron/ 目录 |
| 节点接受外部用户输入后动态渲染字段（表单字段、标签、选项等） | XSS：用户可控字段值通过表达式函数渲染且净化不完整 | 外部数据入口节点（如表单类节点）的字段渲染函数中，evaluateExpression / renderField 等函数的输出是否经过完整 HTML 净化 |

关键判断：**间接 SSRF 比直接 SSRF 更常见**。最危险的情形往往不是 `fetch(user_input)`，而是：
- URL 从数据库读取（攻击者通过上游接口写入了恶意 URL）
- URL 来自第三方 API 的响应（攻击者控制了中间人服务）
- URL 来自文件上传内容（解析阶段提取了链接）

这类间接路径需要在子任务中明确说明，追踪 subagent 才会主动检查。

### 估算规模与拆分粒度

| 项目规模 | 拆分策略 |
|---------|---------|
| 小型 / 单一技术栈，交互类型 ≤3 种 | 直接按交互类型拆分 subagent |
| 中型 / 多模块，交互类型涉及多个独立模块 | 先按类型拆，再按模块拆 |
| Monorepo / 多服务 | 每个含外部交互代码的子包独立处理 |

每个 subagent 负责的文件范围控制在 10–15 个以内，超出则进一步拆分。

## 执行流程

### 段 1：脚本扫描（确定性穷举）

**⚠️ 强制执行 — 必须在段 2 之前完成，不可跳过。**

读取上游 prescan 阶段预执行的扫描结果。验证以下文件是否存在于输出目录：

- `external-summary.txt`（各类别文件数统计，~1KB）
- `external-index.txt`（各类别文件:行号列表，不含代码内容）
- `external-candidates.txt`（完整原始结果，仅调试用）

> 如果文件不存在（prescan 未执行或执行失败），跳过段 1 和段 2，直接执行阶段 A 的手动扫描。**禁止自行编写或执行扫描脚本**。
>
> **降级策略**：若 summary/index 文件缺失，进入全量手动扫描模式，不得因此跳过任何枚举步骤。

**读取顺序（强制）**：
1. 首先读取 `external-summary.txt`（~1KB），了解各类别命中数量
2. 对需要深入的类别，用以下命令按类别提取：
   ```bash
   awk '/^\[CATEGORY_NAME\]$/{f=1;next} /^\[/{f=0} f' "$OUTPUT_DIR/external-index.txt"
   ```
3. 根据提取到的 `文件:行号`，用 Read 工具的 `offset`/`limit` 精准读取源文件
4. **禁止直接读取 `external-candidates.txt` 或整体读取 `external-index.txt`**

### 段 2：补盲搜索

**⚠️ 强制执行 — 段 1 完成后必须执行，不可跳过。即使脚本全部类别都有命中，也必须完整执行段 2 的全部子步骤。**

#### 子步骤 2a：静态盲区补盲（基于 0-files 类别）

1. 回顾段 1 的 `external-summary.txt`，列出所有 `0 files` 的类别
2. 判断决策树：
   - 类别对应项目类型不在 `project_type` 中 → 跳过
   - 该类别为**核心类别** → 必须补盲，不受 Grep 次数限制
   - 其他 0 命中类别 → 执行 1 次 Grep（≤ 3 次）

**外部交互切面核心类别**：

| 核心类别 | 说明 |
|----------|------|
| `HTTP_CLIENT` | 外发 HTTP 请求调用（fetch、axios、requests、HttpClient 等） |
| `FILE_OPERATION` | 文件系统读写操作（open、fopen、readFile、WriteFile 等） |
| `XSS_RENDER` | 节点字段渲染时的 XSS 风险：外部数据入口节点（如 Form 类节点）的字段标签/字段值通过表达式函数动态渲染，且 HTML 净化不完整（sanitizeHtml 漏过 script/event-handler 标签，或缺少 context-aware 输出编码） |

**补盲 Grep 要求**：使用与脚本不同的关键词，禁止重复脚本 pattern。

##### XSS_RENDER 补盲规则（强制执行）

无论脚本命中数量多少，**必须执行 XSS_RENDER 类别检查**。此类别不依赖 0-files 触发条件，因为 XSS 在节点字段渲染场景中的漏报历史上有明确案例。

**检测模式**：

模式 A — 外部数据入口节点 × 表达式渲染 × 不完整净化：
1. 搜索所有节点文件中同时包含以下关键词的代码：
   - 外部数据入口指示：`Form`、`form`、`submit`、`inputField`、`userInput`、`respondWith`
   - 表达式渲染函数：`evaluateExpression`、`renderField`、`getExpressionValue`、`evaluate`
   - HTML 渲染上下文：`innerHTML`、`outerHTML`、`dangerouslySetInnerHTML`、`v-html`（Vue）、`dangerously_html`（Jinja）、`{{`（模板变量未转义）
   - 不完整净化：`sanitizeHtml`、`DOMPurify`、`striptags`、`stripScripts` — 验证是否覆盖了 `<script>`、事件处理器（`onerror`、`onload`、`onclick` 等）、`javascript:` URL、`data:` URL 等高风险向量
2. 确认用户数据（节点参数、trigger 输出数据、工作流表达式结果）流入渲染 Sink

模式 B — webhook 类节点 × 响应内容渲染 × 缺少 Content-Type 或净化：
1. 搜索 `responseBody`、`webhookResponse`、`sendLegacyResponse`、`sendResponse` 等响应渲染函数
2. 验证响应 Content-Type 是否明确设置为 `text/plain` 或 `application/json`，而非依赖默认 `text/html`
3. 验证用户可控数据是否经过 HTML 净化或编码

**可信度验证**（同 2c）：
- 确认命中行不在注释、测试文件、字符串常量中
- 确认外部数据来源可被最终用户控制（非仅工作流管理员）
- 若节点同时有 `sanitizeHtml` 调用，验证净化配置的 `ALLOWED_TAGS` 和 `ALLOWED_ATTR` 是否覆盖了高风险向量

---

#### 子步骤 2b：动态连接目标专项检查（强制执行，不受 0-files 触发约束）

**无论脚本命中多少，必须主动检查以下模式**：
- 运行时动态解析连接目标（URL 从配置/数据库/用户输入获取，非字面量）
- 插件化 HTTP 客户端（通过注册中心获取 client 实例，非直接调用库函数）
- 封装层遮蔽真实调用点（项目自定义 `HttpService`、`ApiClient` 等包装类）

**执行方式**：最多 1 次 Grep（不计入 2a 次数），或 Read 核心 service 类确认是否存在动态连接目标。

---

#### 子步骤 2c：命中结果可信度验证

从 index 提取到 `文件:行号` 后，Read 目标行时必须验证：
1. 目标行不在注释块内
2. 目标行不在测试文件内（路径不含 `test`、`spec`、`mock`、`fixture`）
3. 目标行不是字符串常量
4. 目标行是真实的外部交互调用代码

不满足条件的命中标记为误报，不纳入后续阶段 A/B/C 的语义分析。

---

### 阶段 A：外部交互发现

目标：回答"这个项目通过哪些代码路径与外部系统交互？"

1. 读取项目画像，获取项目类型、技术栈、已知交互点、排除目录
2. 结合诊断阶段的分析，确定需要扫描的交互类型维度和拆分粒度
   - 如果调用上下文指定了关注的 Sink 类别，按指定范围扫描；否则按全量类别扫描
3. Read `refs/interaction-scan.md`，按维度派发扫描 subagent（并发）。向子 agent 传递：
   - `interaction-scan.md` 的完整内容（方法论）
   - 子任务的目标范围（负责的交互类型、目录、模块）
   - 项目背景（语言/框架、已知交互点、排除目录、需关注的 Sink 模式）
4. 汇总所有扫描结果，按业务语义分组为**功能域清单**：
   - 同一业务的多个交互操作合并
   - 跨协议同功能合并
   - 目标地址硬编码、无用户输入路径的极简功能域，标注为低风险，不派发追踪 subagent

### 阶段 B：交互追踪

目标：对每个功能域回答"用户输入能否影响交互目标？响应数据流向哪里？"

1. Read `refs/interaction-trace.md`
2. 为每个功能域派发追踪 subagent（并发）。向子 agent 传递：
   - `interaction-trace.md` 的完整内容（追踪方法论）
   - 子任务的目标（功能域名称、交互点列表）
   - 项目背景（语言/框架、排除目录）
   - 诊断阶段识别的高风险模式（帮助 subagent 聚焦追踪路径）
3. 收集所有追踪 subagent 的功能点分析结果

### 阶段 C：覆盖率审核

目标：确认三个核心问题都被充分回答，没有遗漏的出站通道。

1. Read `refs/interaction-review.md`
2. 派发一个审核 subagent。向子 agent 传递：
   - `interaction-review.md` 的完整内容（审核规则）
   - 项目画像
   - 所有已生成的功能点分析结果
   - 文件读取覆盖率数据（如果调用上下文可提供，用于验证哪些文件未被读取）
3. 根据审核结果处理：
   - **需修复**：派发补充 subagent 覆盖遗漏点或重新追踪
   - **建议改进**：直接修订已有分析结果

## 陷阱和边界条件

### 响应 Sink 追踪容易断链

HTTP 响应体被解析为结构体或 JSON 后，通常经过字段提取、条件过滤、类型转换，才流入危险操作。追踪 subagent 需要从 HTTP 调用处开始追踪响应的完整数据流，而不只是记录"调用了 `http.get`"。如果发现追踪结果只到 HTTP 调用为止、没有覆盖响应去向，主动在补充子任务说明中要求继续追踪。

### 独立脚本是最常见的遗漏

`scripts/`、`bin/`、`cron/`、`jobs/`、`tasks/` 下的脚本不通过 Web 路由触发，极容易在阶段 A 中被略过。在派发扫描任务时，**必须显式分配覆盖这些目录的 subagent**，不能假设它们会被自然发现。这类脚本还有一个特点：它们常将外部数据直接拼入 shell 命令或 SQL，缺少 Web 层的参数校验，风险密度往往高于主业务逻辑。

### 封装层遮蔽了真实调用点

项目常有统一的 HTTP 客户端封装（`httpClient.get()`、`apiClient.fetch()`），实际的底层库调用藏在封装层内。扫描阶段需要同时搜索封装调用和底层库的直接调用——只搜索其中一种会系统性漏报同一类 Sink。告知扫描 subagent 在发现封装层时，也要确认是否存在绕过封装的直接调用。

### 多入口共享同一 Sink 时安全性取决于最弱入口

一个数据库查询函数可能被 REST API handler 和管理后台各调用一次。REST API 有参数校验，管理后台没有。如果追踪只覆盖了有校验的那条路径，结论就是错的。在阶段 B 中，追踪 subagent 应被要求搜索是否存在共享同一 Sink 函数的其他入口点，并比较各入口的输入验证差异。
