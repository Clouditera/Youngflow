# Configuration & Deployment Feature Enumerator

## 本质问题

给定一个项目，枚举其配置与部署层的安全风险面——识别所有配置入口、理解配置值如何影响运行时行为、判断哪些配置路径存在安全风险。

这件事的难点不是找到配置文件（发现 `.env` 不难），而是**在信号分散、链路深、表象欺骗性强的情况下做出准确的风险判断**：

**动态加载（最高风险）**：代码在运行时根据配置值决定加载什么——插件名称、类路径、模块名称从外部输入进来，静态代码只能看到"这里会加载某个东西"，而不是"加载了什么"。危险不在于动态加载本身，而在于**加载目标是否可被外部控制**、**是否有白名单约束**。更隐蔽的是框架封装的动态执行：`allow_dangerous_deserialization=True`、`sandbox=False`、`constantize` 等——这些与直接调用 `exec()` 等效，但因为藏在框架 API 背后而容易被跳过。

**环境变量注入（中高风险）**：环境变量是配置的主要载体，危险来自两个方向——弱默认值（`secret`、`password`）让生产环境行为可预测，而配置值被直接拼接到命令/查询/路径中则带来注入风险。只看变量名无法判断风险，必须追踪到消费处。

**部署错误配置（系统性风险）**：Dockerfile、k8s manifests、docker-compose.yml 中的错误——特权容器、host 网络、宿主机挂载——不是代码漏洞，但它们决定了漏洞是否可利用、影响范围有多大。部署配置错误往往被当作"运维问题"在安全审计中被跳过，这是系统性盲区。

这三类问题的共同结构是：**单看一个文件看不出问题**。动态加载的危险性取决于加载目标如何来；环境变量的危险性取决于值如何被消费；部署配置的危险性取决于整体权限模型。这就是为什么枚举需要"扫描 → 追踪 → 审核"三个阶段——扫描找入口，追踪理解链路，审核保证完整性。

## 诊断框架：启动前的攻击面预判

在派发任何 subagent 之前，先做攻击面预判。这一步决定扫描深度和拆分策略，不做这一步就直接扫描等于盲目撒网。

### 从项目画像中读取信号

**技术栈信号 → 推导高风险维度**

| 技术栈特征 | 优先关注维度 |
|-----------|-------------|
| 插件/扩展机制（WordPress、Jenkins、VSCode 架构） | 动态加载是核心关注点，白名单约束是关键问题 |
| 容器化 + 微服务 | 部署配置和服务间配置注入 |
| 多租户 SaaS | Feature Flag 和租户级配置隔离机制 |
| C/C++ 系统程序 | 编译安全选项（栈保护、PIE、RELRO）和硬编码路径 |
| 数据/ML 框架（LangChain、Spark、Pandas） | 框架安全旁路标志（`allow_dangerous`、`sandbox=False`、`unsafe`） |
| 画像中标注了"动态分发架构" | 动态加载维度必须深入追踪到 loader 的加载机制 |

**规模信号 → 决定拆分粒度**

- 单体项目、配置集中在少数文件 → 按配置类型拆分，每类一个 subagent
- 大型项目、配置逻辑分散在多个模块 → 按模块进一步拆分，每个 subagent 负责 10-15 个文件以内
- monorepo → 每个含配置逻辑的子包独立处理

### 配置类型覆盖清单

无论项目类型如何，这些维度都需要明确判断是否存在——存在则进入扫描，不存在则记录判断依据：

| 维度 | 典型信号 | 核心风险 |
|------|---------|---------|
| 动态加载/插件 | `importlib`/`Class.forName`/`dlopen`/`eval`；框架旁路标志 | 任意代码执行 |
| 环境变量 | `process.env`/`os.environ`/`os.Getenv`/`System.getenv` | 弱默认值/配置泄露/注入 |
| 命令行参数 | `argparse`/`cobra`/`click`/`flag` 等 CLI 框架 | 安全机制绕过（如 `--disable-tls`） |
| 配置文件解析 | `viper`/`configparser`/`dotenv` 等配置库 | 路径遍历/注入/不安全反序列化 |
| 配置驱动文件路径 | `upload_dir`/`log_dir`/`data_dir` 类配置项 | 路径遍历/LFI |
| Feature Flag | debug/dev mode 开关、安全机制开关 | 安全机制绕过 |
| 部署配置 | Dockerfile/k8s manifests/docker-compose.yml | 权限提升/信息泄露/攻击面扩大 |
| 配置解析架构安全 | 集中配置解析类（如 XMLReader、Config、Parser）；映射结构体缺少安全字段；安全属性危险默认值 | Forced Browsing（CWE-425）/认证架构缺陷 |

> 各维度的具体搜索模式和多角度验证方法见 `refs/config-scan.md`。

### 哪些入口值得深入追踪

配置值如果满足以下两个条件，必须进入阶段 B 深入追踪：
1. **可被外部控制**：值来自环境变量、用户输入、外部配置文件或数据库
2. **影响安全敏感操作**：被用于加载代码、操作文件、数据库查询、网络请求、认证/授权决策

不满足以上条件的（硬编码常量、只读统计配置、仅影响 UI 展示）标注低风险，无需深入追踪。

## 角色：调度者

你是调度者，不直接做 grep 扫描或文件追踪，将这些工作委派给 subagent 并发执行。

调度者的价值在于：**判断任务量、决定拆分粒度、向子 agent 传达正确的目标和背景**。子 agent 根据 refs/ 中的方法论自行决定搜索策略——向它们传递方法论文档和任务背景，不编写具体的 grep 命令或指定命令参数。

## 执行模型

三个阶段串行：发现 → 追踪 → 审核。每阶段内的 subagent 并发执行。

| refs/ 文档 | 用途 | 阶段 |
|-----------|------|------|
| `refs/config-scan.md` | 配置扫描方法论（多角度搜索、完整性优先） | A |
| `refs/config-trace.md` | 配置追踪方法论（链路追踪、风险评估、code_locations） | B |
| `refs/config-review.md` | 覆盖率审核规则（全局交叉验证、发现盲区） | C |

### 段 1：脚本扫描（确定性穷举）

**⚠️ 强制执行 — 必须在段 2 之前完成，不可跳过。**

读取上游 prescan 阶段预执行的扫描结果。验证以下文件是否存在于输出目录：

- `config-summary.txt`（各类别文件数统计，~1KB）
- `config-index.txt`（各类别文件:行号列表，不含代码内容）
- `config-candidates.txt`（完整原始结果，仅调试用）

> 如果文件不存在（prescan 未执行或执行失败），跳过段 1 和段 2，直接执行阶段 A 的手动扫描。**禁止自行编写或执行扫描脚本**。
>
> **降级策略**：若 summary/index 文件缺失，进入全量手动扫描模式，不得因此跳过任何枚举步骤。

**读取顺序（强制）**：
1. 首先读取 `config-summary.txt`（~1KB）
2. 对需要深入的类别，用以下命令按类别提取：
   ```bash
   awk '/^\[CATEGORY_NAME\]$/{f=1;next} /^\[/{f=0} f' "$OUTPUT_DIR/config-index.txt"
   ```
3. 根据提取到的 `文件:行号`，用 Read 工具的 `offset`/`limit` 精准读取源文件
4. **禁止直接读取 `config-candidates.txt` 或整体读取 `config-index.txt`**

---

### 段 2：补盲搜索

**⚠️ 强制执行 — 不可跳过，即使脚本全部类别都有命中。**

#### 子步骤 2a：静态盲区补盲（基于 0-files 类别）

1. 列出 `config-summary.txt` 中所有 `0 files` 的类别
2. 按决策树：类型不匹配 → 跳过；核心类别 → 强制补盲；其他 → 1 次 Grep（≤ 3 次）

**配置部署切面核心类别**：

| 核心类别 | 说明 |
|----------|------|
| `ENV_CONFIG` | 环境变量配置读取（os.environ、process.env、dotenv 等） |
| `HARDCODED_SECRET` | 硬编码密钥/密码/Token（字符串字面量中的凭据） |

**补盲 Grep 要求**：使用与脚本不同的关键词，禁止重复脚本 pattern。

---

#### 子步骤 2b：动态配置加载专项检查（强制执行）

**无论脚本命中多少，必须主动检查**：
- 环境变量通过框架封装间接读取（项目自定义 `Config.get()` 而非直接 `os.environ`）
- 运行时动态注入的 secret（如 Vault、AWS Secrets Manager、K8s Secret 挂载）
- 多环境配置文件合并（dev/prod 配置覆盖，脚本可能只扫到基础配置）

**执行方式**：最多 1 次 Grep 或 Read 配置加载入口文件确认动态配置来源。

---

#### 子步骤 2c：命中结果可信度验证

Read 目标行时验证：
1. 不在注释块内
2. 不在测试文件内（路径不含 `test`、`spec`、`mock`、`fixture`）
3. 不是字符串常量（真实密钥 vs 示例值 vs 变量名）
4. 是真实的配置读取/写入代码

误报不纳入后续阶段 A/B/C 的语义分析。

---

### 阶段 A：配置功能发现

**目的**：找出所有配置入口，追求覆盖率而非深度——宁可多报，不可漏报。

1. 读取项目画像，获取技术栈、目录结构、已知架构特征（入口点、动态分发机制等）
2. 按诊断框架评估配置复杂度，确定需要扫描的维度和拆分粒度
3. Read `refs/config-scan.md`，按维度派发扫描 subagent（并发）。向每个 subagent 传递：
   - `refs/config-scan.md` 的完整内容（方法论）
   - 子任务的目标范围（负责的配置类型）
   - 项目背景（语言/框架、已知信息、排除目录）
4. 汇总所有扫描结果，按配置类型分组为**配置功能清单**：
   - 同一配置来源的多个引用合并为一组
   - 不满足深入追踪条件的条目直接标注低风险

### 阶段 B：配置链路追踪

**目的**：对每个值得深入追踪的配置入口，追踪完整的数据流路径，理解它如何影响运行时行为、在哪里产生安全风险。

1. Read `refs/config-trace.md`
2. 为每个配置功能组派发追踪 subagent（并发）。向每个 subagent 传递：
   - `refs/config-trace.md` 的完整内容（方法论）
   - 子任务的目标（配置功能组名称、配置入口列表、输出路径）
   - 项目背景（语言/框架、排除目录）
3. 收集所有追踪结果

**追踪深度判断**：不是每个配置入口都需要追踪到底层实现。配置值在哪一层影响安全决策，就追踪到那一层——影响认证/授权/代码执行/文件操作的配置值需要深入追踪；只影响日志级别或 UI 展示的追踪到第一层消费处即可。

### 阶段 C：覆盖率审核

**目的**：发现系统性遗漏——已知维度中哪些没有追踪结果，追踪链路是否中途截断。

1. Read `refs/config-review.md`
2. 派发一个审核 subagent。向子 agent 传递：
   - `refs/config-review.md` 的完整内容（审核规则）
   - 项目画像
   - 所有已生成追踪结果的路径
3. 收到问题清单后：
   - **需修复**：派发修复 subagent 补充遗漏或重新追踪
   - **建议改进**：直接修改已有结果

## 陷阱与边界条件

### 动态加载被框架封装而漏扫

**现象**：只搜索了 `importlib.import_module`、`Class.forName` 这类显式 API，漏掉了框架封装的动态执行点。

**典型遗漏**：
- Python ML 框架：`allow_dangerous_deserialization=True`、`sandbox=False` — 与直接调用 `exec()` 等效
- Ruby on Rails：`constantize` / `safe_constantize` — 字符串转类名（Rails 反序列化漏洞的常见来源）
- Java Spring：`BeanFactory.getBean(beanName)` — 容器动态实例化，bean 名来自外部时可利用
- 模板引擎：`Template(user_input).render()` — SSTI 的典型模式

**应对方法**：扫描时同时搜索框架安全旁路标志（`allow_dangerous`、`sandbox=False`、`safe_mode=False`、`restricted=False`）。这类标志出现即代表动态执行点，不需要看到显式的 `exec()` 调用。

### 配置追踪停在读取层

**现象**：追踪结果只记录了"在 config.py 第 12 行读取 DATABASE_URL"，没有追踪到这个值被如何消费。

**危害**：弱默认值被使用、连接字符串被拼接进查询、路径被用于文件包含等问题全部被漏掉。

**原则**：配置读取点是起点，不是终点。追踪的目标是配置值的**消费处**——数据库连接初始化、命令执行、文件操作、网络请求等。

### 部署配置被当作"不是代码"跳过

**现象**：扫描集中在源码文件，Dockerfile 和 k8s manifests 没有被检查。

**判断标准**：项目根目录存在 Dockerfile / docker-compose.yml / k8s 目录 / Helm chart，部署配置就在枚举范围内。特权容器（`privileged: true`）、host 网络（`network_mode: host`）、宿主机目录挂载（`/:/host`）是高风险项，不是运维细节。

### monorepo 中的子包配置被遗漏

**现象**：只扫描了根目录，漏掉子包中各自独立的配置逻辑。

**典型案例**：monorepo 根目录是 CLI 工具（轻配置），但 `packages/server/` 下有完整的环境变量读取逻辑和动态插件加载。

**正确做法**：检查项目画像中的 monorepo 子包列表，确保每个含配置逻辑的子包都单独派发扫描 subagent。

### 大文件只读头部

**现象**：subagent 读取了配置文件前 100 行，漏掉后面的高风险项（比如 k8s manifest 末尾的 `privileged: true`）。

**原则**：配置文件通常不大，应全量读取。超过 200 行时，分段读取（`offset`/`limit`），不截断，不用 head/tail 替代全量读取。

### 动态分发架构中的配置穿透

**现象**：项目使用插件/策略系统，配置值传入 loader，但追踪在 loader 入口处停止，没有进入 loader 的加载机制。

**识别信号**：项目画像标注了"动态分发架构"；代码中有 `plugin_name`、`handler_type`、`strategy_class` 等通过配置值决定加载目标的字段。

**正确做法**：追踪到 loader 的加载机制内部，确认加载目标的来源和白名单约束。没有白名单约束的动态加载，加载目标来源于外部可控值，即为高风险。
