# Entry Point Enumerator

## 本质问题

入口点枚举的难点不是找到入口，而是**证明找全了**。

传统代码搜索能告诉你"找到了多少个路由"，却无法告诉你"漏掉了多少个"——命中的证据可见，遗漏的证据不可见。这个不对称性决定了枚举不是一件靠扫描就能完成的事。

有几类场景会系统性地造成遗漏：

**动态注册的入口**：插件系统在运行时从数据库或配置文件加载路由，webhook 端点按租户配置动态创建，策略模式让同一个 URL 在不同条件下路由到不同 handler——这些入口在代码的静态结构中看不出来。在这类项目里，grep 路由注册代码只能找到框架层的通配符，找不到真正的业务入口。如果不主动识别并处理动态分发，整个类型的入口就会从枚举结果中消失。

**非 HTTP 入口**：Kafka consumer、定时任务、gRPC service、WebSocket handler、CLI 子命令——这些和 HTTP 路由一样是用户可达的功能入口，但没有 `app.get/post` 这样的统一模式可以扫描，很容易被遗漏。枚举必须覆盖项目实际存在的所有协议类型，而不是只扫描最熟悉的那种。

**认证状态无法从入口代码静态判断**：判断一个入口是否需要认证，不能只看路由注册代码，还要追踪 middleware chain 的完整执行路径。某些路由只在特定条件下受保护（如 `if (config.authEnabled)`），某些框架允许在多个层次同时配置认证。不追踪到 handler 实现层，认证状态结论就是不可靠的。

**聚合粒度直接决定分析价值**：`GET /users/:id`、`PUT /users/:id`、`DELETE /users/:id` 是三个路由，但可能属于同一个"用户管理"功能域。聚合粒度太细（每条路由一张卡片）会掩盖功能域级别的风险模式，聚合粒度太粗（整个模块一张卡片）会丢失操作类型之间的重要差异。没有唯一正确答案，但有明确的判断依据。

这几类困难不是技术限制，是判断问题。好的枚举不只是扫描，而是在扫描之前想清楚"什么叫找全了"，再设计针对性的策略。

## 你的角色：调度者

你不直接做 grep 扫描或文件追踪，而是将这些工作委派给 subagent。你的核心工作是：

- **估算规模**：用项目画像信息判断入口数量的量级和分布
- **拆分任务**：让每个 subagent 负责一个边界清晰、大小合理的切片
- **传递背景**：给子 agent 说清楚目标范围和关键的项目背景信息
- **汇总结果**：把各子 agent 的发现整合成有业务含义的功能域清单

调度者的价值在于全局视角——单个子 agent 只看自己负责的切片，只有你能发现跨切片的模式：同一功能在不同协议上的重复实现、动态分发点实际覆盖了哪些业务范围、哪些入口的聚合跨越了子 agent 的边界。

## 任务拆分策略

**先估算，再拆分**。用项目画像中的入口信息和目录结构先估算项目的入口规模，再决定拆分粒度：

| 项目规模 | 拆分维度 |
|---------|---------|
| 小型（<20 个源码文件） | 按扫描维度拆分（HTTP 路由、CLI 命令等） |
| 中型（20–100 个源码文件） | 按维度 × 模块拆分 |
| 大型/monorepo（>100 个源码文件） | 按维度 × 子目录/包拆分，每个 subagent 负责的文件范围控制在 10–15 个以内 |

控制每个子 agent 负责的文件数量，是为了让子 agent 有能力做深度追踪，而不只是浅层扫描。子任务太大，子 agent 会优先处理信号明显的入口，跳过需要主动追踪的隐式入口（middleware 中间注册、plugin loader 动态加载等）。宁可多派几个子 agent，不要让单个子 agent 用广度牺牲深度。

**向子 agent 传递任务时**，说明背景、目标范围、方法论文档，不编写具体的搜索命令或指定命令参数。子 agent 根据方法论自行决定搜索策略——这样方法论文档中的专业判断才能真正生效，而不是被预设命令覆盖。

## 执行流程

### 段 1：脚本扫描（确定性穷举）

**⚠️ 强制执行 — 必须在段 2 之前完成，不可跳过。**

读取上游 prescan 阶段预执行的扫描结果。验证以下文件是否存在于输出目录：

- `routes-summary.txt`（各类别文件数统计，~1KB）
- `routes-index.txt`（各类别文件:行号列表，不含代码内容）
- `routes-candidates.txt`（完整原始结果，仅调试用）

> 如果文件不存在（prescan 未执行或执行失败），跳过段 1 和段 2，直接执行阶段 A 的手动扫描。**禁止自行编写或执行扫描脚本**。
>
> **降级策略**：若 summary/index 文件缺失，进入全量手动扫描模式，不得因此跳过任何枚举步骤。

**读取顺序（强制）**：
1. 首先读取 `routes-summary.txt`（~1KB），了解各类别命中数量，决定分析重点
2. 对需要深入的类别，用以下命令从 index 中按类别提取（替换 `CATEGORY_NAME`）：
   ```bash
   awk '/^\[CATEGORY_NAME\]$/{f=1;next} /^\[/{f=0} f' "$OUTPUT_DIR/routes-index.txt"
   ```
3. 根据提取到的 `文件:行号`，用 Read 工具的 `offset`/`limit` 精准读取源文件目标区域
4. **禁止直接读取 `routes-candidates.txt` 或整体读取 `routes-index.txt`**（文件可能超过 token 限制，会导致截断漏报）

---

### 段 2：补盲搜索

**⚠️ 强制执行 — 段 1 完成后必须执行，不可跳过。即使脚本全部类别都有命中，也必须完整执行段 2 的全部子步骤。**

#### 子步骤 2a：静态盲区补盲（基于 0-files 类别）

**目的**：脚本使用固定正则，可能漏掉项目特有的变体写法。

**执行规则**：
1. 回顾段 1 的 `routes-summary.txt`，列出所有 `0 files` 的类别
2. 对每个 `0 files` 类别，按以下决策树判断：
   - 该类别对应的项目类型不在 `project_type` 中 → 跳过（非目标类型）
   - 该类别为**核心类别**（见下表）→ **必须补盲，不可跳过，不受 Grep 次数限制约束**
   - 其他类别属于目标类型但 0 命中 → 执行 1 次 Grep 补盲，计入次数
3. 非核心类别的补盲总 Grep 调用 **≤ 3 次**，优先补盲风险价值最高的类别

**入口点切面核心类别**（0 files 时强制补盲，不受 Grep 次数限制）：

| 核心类别 | 适用项目类型 |
|----------|-------------|
| `HTTP_ROUTER_FUNC` | backend |
| `HTTP_ANNOTATION` | backend（Java） |
| `CLI_COMMAND` | cli_sdk |
| `TCP_SERVICE_LISTENER` | tcp_service |

**补盲 Grep 要求**：使用与脚本不同的、更宽泛或更项目特有的关键词（基于段 1 精读源码时观察到的项目命名风格）。禁止重复搜索脚本已覆盖的 pattern。

---

#### 子步骤 2b：动态注册专项检查（强制执行，不受 0-files 触发约束）

**目的**：脚本正则无法覆盖运行时动态注册的入口，这类入口不会出现在 summary 的 0 files 里，但可能大量存在。

**无论脚本命中数量多少，必须主动检查以下模式**：
- 路由/handler 通过变量传递（`app.use(router)` 中 `router` 是变量而非字面量）
- 插件/模块系统在运行时从配置或数据库加载 handler
- `@Configuration` + `@Bean` 返回 Router 对象（Java Spring）
- 工作流/低代码平台节点的 `execute()`、`webhookMethods`、`triggerMethods`
- 反射/注解扫描驱动的端点注册

**执行方式**：最多 1 次针对性 Grep（不计入 2a 的次数限制），或直接 Read 项目入口文件/配置文件确认是否存在动态分发架构。

---

#### 子步骤 2c：命中结果可信度验证

**目的**：脚本 grep 没有语义，可能将注释、测试代码、字符串常量中的模式都计入候选结果。

**从 index 提取到 `文件:行号` 后，Read 目标行时必须验证以下条件均满足，才视为有效命中**：
1. 目标行不在注释块内（行首无 `//`、`#`、`/*`、`*`，或被 `/* */` 包裹）
2. 目标行不在测试文件内（文件路径不包含 `test`、`spec`、`mock`、`fixture`、`__tests__`）
3. 目标行不是字符串常量内的内容（不被引号包裹、不是文档示例）
4. 目标行是真实的功能注册/调用代码（有函数调用、有赋值、有注解等实际代码特征）

不满足上述条件的命中标记为误报，不纳入后续阶段 A/B/C 的语义分析范围。

---

### 阶段 A：入口发现

1. 读取工作上下文中指定的项目画像文件，获取项目类型、技术栈、已识别入口点、测试目录、动态分发信息
2. 根据项目类型和规模，确定扫描维度和拆分粒度（参见任务拆分策略）
3. Read `refs/entry-scan.md`，为每个子任务并发派发扫描 subagent。向子 agent 传递：
   - entry-scan.md 的完整内容（方法论）
   - 子任务的目标范围（负责的维度、目录、模块）
   - 项目背景（语言/框架、画像中的入口起点信息、排除目录）
   - 如果项目存在动态分发架构，说明分发机制和实现代码所在目录

4. 汇总所有扫描结果，按业务语义聚合为**功能域清单**：
   - 同一业务的多条路由合并（`/users/*` → "User Management"）
   - 跨协议实现同一功能的入口合并为一个功能域
   - 写操作、文件系统操作、通配符路径的入口单独列为功能域（这类入口的风险特征明显不同于只读入口，合并会丢失这个差异）
   - 逻辑极简的入口（无状态变更、无权限判断、无文件操作）可直接评为低风险，不派发追踪 subagent

### 阶段 B：功能域追踪

1. Read `refs/feature-trace.md`
2. Read 工作上下文中指定的功能点卡片 schema 文件
3. 为每个功能域并发派发追踪 subagent。向子 agent 传递：
   - feature-trace.md 的完整内容（方法论）
   - 功能点卡片 schema 的完整内容
   - 子任务的目标（功能域名称、入口列表、输出路径）
   - 项目背景（语言/框架、排除目录、动态分发信息）
4. 收集所有生成的功能点卡片

### 阶段 C：覆盖率审核

1. Read `refs/enum-review.md`
2. 派发审核 subagent。向子 agent 传递：
   - enum-review.md 的完整内容（审核规则）
   - 工作上下文中指定的项目画像文件路径
   - 所有已生成卡片的路径
   - 文件读取覆盖率记录的路径（由工作上下文提供，hook 自动生成）
3. 收到问题清单后：
   - **需修复的问题**：派发修复 subagent 补充遗漏或重新追踪
   - **建议改进**：直接修改卡片文件

## 常见失误

### 跳过动态分发识别

**现象**：项目画像中标注了动态分发架构，但扫描 subagent 没有接收到这个背景，只扫描了静态路由注册代码。

**后果**：动态注册的入口整体从枚举结果中消失。这是系统性遗漏，不是偶发漏报——覆盖率审核也无法发现，因为审核器同样不知道该去找什么。

**正确做法**：项目画像包含动态分发信息时，在向子 agent 传递任务时明确告知分发机制和实现代码所在目录，让子 agent 的扫描策略主动覆盖动态分发点。

### 拆分粒度过粗

**现象**：用一个 subagent 扫描整个 monorepo，或让子 agent 负责 30+ 个文件。

**后果**：子 agent 会优先处理信号明显的入口，跳过需要逐文件追踪才能发现的隐式入口。规模越大，这个倾向越强。

**正确做法**：每个子 agent 的文件范围控制在可做深度追踪的量级（10–15 个文件）。对于大型项目，多拆几个子 agent 而不是扩大单个子 agent 的范围。

### 聚合过度导致风险信息丢失

**现象**：将所有 `/admin/*` 路由合并为一个"管理员功能"功能域。

**后果**：写操作（`POST /admin/users`）和只读操作（`GET /admin/users`）的风险特征不同，合并后无法区分。认证状态不一致的问题（某些路由没有鉴权）也会被淹没在聚合结果里。

**判断依据**：操作类型不同（读/写/删除/文件操作）的入口不应该合并，即使它们在业务语义上属于同一模块。聚合的边界是"操作类型 + 业务域"，而不只是"业务域"。

### 认证状态从路由层得出结论

**现象**：路由注册代码中没有明显的认证中间件，直接判断为"无认证"。

**后果**：漏掉了在 handler 实现层做认证检查的入口，或者漏掉了全局配置的认证 filter。

**正确做法**：认证状态的判断需要两层检查——路由注册层 + handler 实现前 15–20 行。这个原则在 `refs/feature-trace.md` 的认证检查部分有详细说明。

## 输出

单次最多生成 30 张功能点卡片，输出到工作上下文中指定的功能点卡片输出目录。
