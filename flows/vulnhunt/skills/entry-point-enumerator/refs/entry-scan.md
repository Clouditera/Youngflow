# 入口扫描方法论

## 任务目标

在指定范围内发现所有用户可达入口点，输出完整的入口清单。完整性是第一优先级——宁可多报，不可漏报。

## 方法论

### 搜索完整性

- **多角度交叉验证**：对同一类入口，用至少 3 种不同的搜索模式验证，避免单一模式的盲区
- **不截断搜索结果**：禁止对搜索结果做 head/tail 截断。如果结果过多，按子目录分批搜索缩小范围
- **目录广度覆盖**：扫描所有源码目录，不局限于 `src/`。monorepo 中每个包都要检查
- **隐式入口不遗漏**：约定路由（目录结构即路由）、事件监听器、消息消费者、定时任务、框架自动注册端点

### 验证要求

- 搜索命中必须验证：确认是实际入口注册，不是注释、测试或字符串常量
- 对大文件或搜索结果密集的文件，Read 确认上下文

### C 项目命令处理函数完整扫描

在 C 项目中（如 Redis、Nginx、PostgreSQL 等），命令处理函数通常按功能模块组织在同一个源文件中，每个文件可能包含数十个命令函数。例如一个 `t_stream.c` 文件可能包含 XADD、XREAD、XACK、XACKDEL、XDEL 等十余个命令，分布在文件的不同区域（开头、中间、末尾）。

**扫描策略**：

- **按文件全量搜索，不按行数截断**：对一个源文件中的命令入口，用 grep 搜索 `void.*Command\(client` 或命令注册数组中的条目模式（如 `Command` 或 `CommandType` 结尾的函数指针），覆盖该文件包含的所有命令
- **大文件必须完整扫描**：文件行数可能达数千行（如 Redis 的 `t_stream.c` 超过 4000 行），扫描时不得只读文件开头的前几百行就停止。每个文件的扫描深度应与其行数匹配
- **搜索而非逐行阅读**：对于大文件，先用 Grep 定位所有命令函数的行号，再按需读取具体函数体。禁止从头逐行阅读大文件
- **验证命令分发注册**：确认搜索到的命令函数是否真正注册到命令分发表中，排除仅被其他命令内部调用的辅助函数

### C 项目内部处理函数追踪

对于 C 语言项目（如 Redis、Memcached、Nginx 等），用户入口往往是顶层命令处理函数（如 `PFADD`、`GET`、`SET`），但漏洞也可能存在于这些入口函数内部调用的辅助函数中。单纯扫描顶层入口点会遗漏内部漏洞函数。

当发现命令处理入口时，应进一步追踪其内部调用链：

1. **定位命令处理函数**：在 `src/` 目录下搜索项目特定的命令注册模式（如 Redis 的 `RedisModule_CreateCommand`、Nginx 的 handler 注册等），找到顶层命令入口
2. **追踪内部辅助函数**：对每个命令处理函数，Read 其实现并追踪内部调用的辅助函数。这些辅助函数往往：
   - 位于同一文件或同模块内
   - 命名模式包含 `RegHisto`、`Decode`、`Parse`、`Process`、`Encode`、`Convert`、`Validate`、`Normalize` 等后缀
   - 承担核心的数据解析、转换或校验逻辑
3. **覆盖内部函数作为潜在入口**：将上述内部辅助函数也记录为潜在漏洞入口点，标记"由 {命令入口} 内部调用"
4. **注意隐式调用链**：某些内部函数被多个命令入口共享（如 `*SparseRegHisto` 被 `PFCOUNT` 等多个命令间接调用），需确保追踪完整

### 动态分发入口

如果项目存在动态分发架构（入口通过运行时配置路由到不同实现）：

1. 分发入口本身记录为入口点，标记"动态分发"
2. 实现目录下的每个模块也记录为潜在入口点
3. 实现模块中的入口标记"由 {dispatch_entry} 动态调用"

## 输出格式

每个入口一行，用 `|` 分隔：

```
协议类型 | 路径/标识 | 文件 | 行号 | 备注
```

示例：
```
http | GET /api/users | UserController.java | 45 | @RequestMapping
http | POST /webhook/:path | WebhookController.ts | 12 | 动态分发
ws | /ws/notifications | NotificationHandler.java | 30 | WebSocket endpoint
cli | backup create | backup.go | 55 | cobra subcommand
```

## 常见陷阱

### 大文件命令截断

**现象**：对包含多个命令处理函数的源文件只扫描了前半部分（如文件前 2000 行），漏掉了文件后半部分的命令（如 `xackdelCommand`、`xdelCommand` 等），导致入口枚举不完整

**原因**：没有意识到同一个文件可能包含分布在不同区域的十余个命令函数；或对大文件采用了固定行数截断的读取策略

**正确做法**：对 C 项目，先用 grep 搜索整个文件找到所有 `*Command(client` 模式的函数定义，覆盖文件的全部行号范围。对超过 2000 行的大文件尤其要注意后半部分的命令分布

### 按固定行数截断大文件

**现象**：对大源文件设置了"只读前 N 行"的策略（如前 500 行），导致后半部分的命令入口全部漏报

**原因**：错误地认为命令入口只集中在文件开头

**正确做法**：C 项目中命令函数遍布文件各处（开头、中间、末尾），不存在"命令集中在文件前半"的规律。必须对整个文件执行搜索，不用行数限制筛选结果
